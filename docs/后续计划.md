# 后续计划

> 下面各项代码均已实现。保留这些文字作为设计依据和排障参考，不再是待办清单。

## 开机自启动

在设置里增加「开机自启动」开关，默认关闭。

- 开启时写入当前用户的 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值为 `AdbDeviceVitals.exe` 的完整路径。不请求管理员权限。这是 Windows 的启动登记机制，不算用户配置。
- 关闭时删除该项。
- 程序路径变化后，下次启动时按 `settings.json` 里的开关重新登记，不用等用户再保存一次设置。
- 自启动后进入系统托盘，不弹出主窗口。已有实例在运行时，沿用现有单实例逻辑，不再启动第二份进程。

开关与现有 ADB 目录一起保存在 `~/adb-device-vitals/settings.json`，详见文末「实现说明：配置文件」。

## 启动后自动开启 USB 网络共享

程序启动后（含开机自启动和手动启动）自动查找设备，并在 USB 网络共享未开启时尝试打开。该行为单独做成设置项，默认关闭，避免未经选择就改手机的 USB 模式。

流程：

1. 沿用现有逻辑定位 `adb.exe`，执行 `adb devices`，只处理状态为 `device` 的已授权设备。多台在线时按设置里指定的目标设备处理，详见文末「实现说明：多设备下的目标设备」。
2. 读取 `dumpsys tethering`。已有 `rndis*` 或 `ncm*` 处于 `TetheredState` 且 `lastError = 0` 时，视为已开启，不再切换 USB 功能。
3. 未开启时执行 `svc usb setFunctions rndis,adb`，保留 ADB，避免调试连接被切掉。（实际实现只下发 `rndis`，差异与原因见文末「实现说明」）
4. USB 重新枚举后等待设备重新出现，再次读取 `dumpsys tethering` 确认结果。
5. 登录后手机或 ADB 可能尚未就绪。在一段时间内按间隔重试查找和开启，成功、用户关闭该设置，或进程退出后停止。

失败时只在界面和托盘提示原因，不反复改 USB 模式：

- 找不到 `adb.exe`
- 没有设备，或设备为 `unauthorized`
- `svc usb setFunctions` 执行失败
- 命令成功但共享仍未进入 `TetheredState`（部分厂商不会因此拉起 NAT/DHCP，或运营商禁止网络共享）

已开启时不做开关切换。主窗口早期有「USB 共享」手动开关（`svc usb setFunctions mtp`），后来按界面精简需求移除；关闭共享现在由用户在手机系统设置里操作，不属于本程序的自动流程。服务层 `SetEnabledAsync(false, ...)` 仍保留，但当前 UI 没有调用它的入口。

## 实现说明：USB 功能组合保持 `rndis`

上一节流程的第 3 步，实际实现为 `svc usb setFunctions rndis`，不显式带 adb。**这个差异是有意保留的，现状不做改动。**

原因：

- `setFunctions` 是"替换整个组合"语义，按字面执行时不含 adb 就会摘掉调试通道。但在验证机型（小米 M2102K1AC）上下发 `rndis` 后，`getprop sys.usb.state` 仍为 `rndis,adb`，系统自己把 adb 并了回来，调试连接没有中断。
- 因此在验证机型上，显式写 `rndis,adb` 收益为零，反而多一条可能因厂商实现差异而失败的命令，故维持 `rndis`。
- 这个做法依赖 ROM 行为，不是协议保证。若某机型严格按 AOSP 语义只保留 `rndis`，切换后 ADB 会掉线：`ConfirmAsync` 等不到设备重新上线，会把已经成功的切换报成「USB 功能已切换，但网络共享未进入 TetheredState」，界面上也无法再用 `setFunctions mtp` 关闭共享，只能到手机上操作。遇到这种机型时，再把 `EnableFunctionCommand` 改回 `svc usb setFunctions rndis,adb`。
- 另外，`setFunctions` 只改运行时组合，不写入 `persist.sys.usb.config`。拔插数据线或重启手机后，USB 功能回到系统持久化的组合（通常只含 adb 或 `mtp,adb`），共享不会自动恢复，因此"切完靠 USB 重枚举再连回来"并不成立，不能当作恢复手段。

## 启动后自动开启电脑热点

把已经进到电脑里的手机网络，再用 Wi-Fi 分给其他设备。设置项 `AutoStartPcHotspot` 默认关闭，与 ADB 目录一起保存在 `settings.json`。

流程：

1. 开机链路在 USB 网络共享那一步落定后触发；若「启动后自动开启 USB 网络共享」未开启，则启动时直接触发。
2. 遍历 `NetworkInformation.GetConnectionProfiles()`，按网卡驱动描述匹配手机共享出来的网卡（`Remote NDIS Compatible Device`、`NCM` 等），取连通性最高的一条作为上游。
3. 上游还没拿到地址时按 3 秒间隔重试，最长 120 秒；超时只提示一次，不无限重试。
4. 以该配置文件创建 `NetworkOperatorTetheringManager`，先用 `GetTetheringCapabilityFromConnectionProfile` 检查系统是否允许，再 `StartTetheringAsync`，最后确认 `TetheringOperationalState` 落到 `On`。

**不能用默认路由当上游**：`GetInternetConnectionProfile()` 返回的是默认路由，电脑同时连着别的网络时（比如办公室 Wi-Fi），热点会把那个网络共享出去，而不是手机流量。必须按网卡描述找 RNDIS/NCM 那块网卡。

实现细节与踩到的坑：

- 早期 WinForms / .NET Framework 版本受"只用系统自带编译器、零 NuGet"的约束，WinRT 全部走反射，靠轮询 `IAsyncInfo.Status`（`0=Started`、`1=Completed`、`2=Canceled`、`3=Error`）再取结果；异步对象在运行时是 `__ComObject`，`GetResults` 要从方法声明的返回类型上找。**全量迁移到 `net10.0-windows10.0.19041.0` 后这套反射已删除**，改为 CsWinRT 强类型 API：`NetworkInformation.GetConnectionProfiles()`、`NetworkOperatorTetheringManager.CreateFromConnectionProfile(...)`、`await StartTetheringAsync()` / `StopTetheringAsync()`，直接读 `NetworkOperatorTetheringOperationResult.Status`。上游查找、能力检查、确认窗口、错误文案全部保持不变。
- `TetheringOperationalState` 的取值是 `Unknown = 0`、`On = 1`、`Off = 2`、`InTransition = 3`，**不是**按名字直觉排列。最初按 `Off = 0` 映射，结果关掉的热点被读成"切换中"，一直报"热点仍在运行"。迁移后仍沿用这套映射。
- 读状态要重新创建 manager，复用同一个对象拿到的是旧值。
- 系统从 `InTransition` 落到 `On` / `Off` 通常一秒内完成，确认窗口取 20 秒、间隔 1 秒即可。

界面早期把它单独放在底部一行「电脑热点」，与读手机侧状态（`dumpsys tethering` / `dumpsys wifi`）的「网络共享」卡片分开，避免混淆。后来按界面精简需求改为：开关放进「网络共享」卡片右上角（文字写「开启热点」并带 ToolTip 注明是电脑侧），底部「电脑热点」一行只保留状态文字。再之后用户要求第二张卡片只关注上下行，于是把开关移回底部「电脑热点」行右侧（与状态同列），卡片标题改为「网速」、只显示 ↓ / ↑ 两个数值，手机侧共享明细移到卡片悬停提示。两者含义始终不同，靠文案和提示区分。

热点由 Windows 的 ICS 服务提供，客户端会拿到 `192.168.137.x` 的地址。程序退出不会关闭热点。

## 实现说明：多设备下的目标设备

同时连接多台 Android 设备时，原来的 `FirstAuthorized(devices)`（取列表第一台已授权设备）会埋一个隐患：状态卡片看着 A 手机，USB 共享的自动操作却可能切到 B 手机，而 `setFunctions` 改的是那台手机的 USB 功能组合。因此改为统一由 `Services/DeviceSelection.cs` 的纯函数 `Resolve(devices, preferredSerial)` 决定目标，**监控采集（`DeviceMonitor`）和共享服务（`UsbTetheringService`）都调用它**，保证两处看到的是同一台设备。

判定规则：

| 情况 | 结果 |
|---|---|
| 没有已授权设备 | 提示授权 USB 调试 / 未找到设备 |
| 未记录序列号，只有 1 台 | 直接用它（保持零配置的即插即用） |
| 未记录序列号，多台 | 返回「请在设置中指定用于网络共享的设备」 |
| 记录了序列号，且在线已授权 | 精确锁定该设备，与列表顺序无关 |
| 记录了序列号，但当前不在已授权列表中 | 返回「预设的设备（xxx）未连接，请在设置中从当前设备列表重新选择」 |

最后一行是**刻意不降级**：即使当前只剩一台别的手机，也不会自动改用那台。换手机、换 USB 口、设备临时离线这些情况都应该由人确认，而不是猜。设备在线但状态是 `unauthorized` / `offline` 同样算「不在列表」。

设置项 `TargetDeviceSerial` 与其他配置一起存在 `settings.json`，值为字符串，空表示自动模式；读取时用 `DeviceSelection.IsValidSerial` 校验，与 `AdbClient.RunShellAsync` 拼 `-s <serial>` 前的正则一致，避免手改配置文件写进非法命令。

各条路径上的表现：

- **设置页**：下拉框列出「自动选择」+ 当前已授权设备；若记录的设备不在列表，额外追加一项 `⚠ 预设设备 xxx 未连接，请重新选择` 并默认选中，下方橙红色说明；此时保存会被拦下，必须先重新选。「刷新列表」按钮可在不关窗口的情况下重新读取 `adb devices`（改了 ADB 目录需先保存、重开设置）。
- **主窗口**：`DeviceSnapshot` 增加 `NeedsDeviceSelection` / `PreferredSerialMissing`。顶部状态显示短提示并支持点击打开设置（空间有限，完整原因放托盘气泡）；USB 共享相关的自动操作全部暂停。手动 USB 共享开关已移除。
- **自动开启共享**：`EnsureCoreAsync` 把「目标设备未就绪」当作等待原因，在 3 分钟 discovery 窗口内继续等，不会顺手用列表里的其它设备；超时后把提示显示出来。
- **掉线恢复**：目标设备未就绪时状态机不会插手，不执行 `setFunctions`。

`ConfirmAsync` 仍按命令下发时的序列号判断设备是否重新上线，切换 USB 功能后即使旁边还有别的手机在线，也不会把确认结果算到它们头上。

## 实现说明：配置文件

配置不再放 `HKCU\Software\AdbDeviceVitals`，改为 `~/adb-device-vitals/settings.json`（通过 `Environment.SpecialFolder.UserProfile` 解析，不是 exe 所在目录）。字段沿用旧注册表值名，迁移时无需映射：`AdbDirectory`、`TargetDeviceSerial`、`RunAtStartup`、`AutoEnableUsbTethering`、`AutoStartPcHotspot`、`LastUpdateCheckUtc`，外加一个 `schema` 版本号。后来新增的 `AutoRecoverUsbTethering`（默认关闭）、`SmsSyncEnabled`（默认关闭）、`SmsToastEnabled`（默认开启）与 `SmsSenderFilter`（默认为空）不在旧键里，旧文件缺字段时按各自的默认值处理。

- **格式**：手写极简 JSON 编解码，放在 `Services/SettingsFile.cs` 里做纯函数。最初是为了在"系统自带编译器、零 NuGet"的构建方式下不引入 JSON 库；迁移到 .NET 10 后**没有改用 `System.Text.Json`**，字段、宽容解析和单测断言都保持原样（未知字段忽略、写坏的字段跳过，坏一项不丢整份配置），避免升级时配置行为漂移。`UpdateChecker` 读 GitHub JSON 仍用正则。
- **缓存**：`AppSettings` 保留全部静态属性的签名，内部改为带锁的内存快照。轮询每 2.5 秒读一次 `TargetDeviceSerial`，USB 共享等待循环也反复读 `AutoEnableUsbTethering`，getter 绝不能碰磁盘。只在启动（`Initialize`）、打开设置（`Reload`）和保存（`Save` / 属性 setter）时读写文件；写盘成功后才更新缓存，所以设置页保存后 `_adb.ReloadPath()` 立即拿到新值。
- **原子写**：同目录 `settings.json.tmp` → `File.Replace`（首次创建则 `File.Move`），UTF-8 无 BOM。设置页原来是逐个属性写 5 次注册表，现在一次 `Save(SettingsData)` 写整份，不留下中间状态。写失败抛给设置页提示，内存保持旧值；`LastUpdateCheckUtc` 写失败仍静默。
- **一次性迁移**：文件不存在时读旧键生成文件，成功后在旧键写 `MigratedTo` 标记。**标记是关键**：否则用户删掉 `settings.json` 想重置时，下次启动又会被旧注册表值灌回来。旧值本身不删，回滚到 0.0.6 仍可用。迁移时对 `TargetDeviceSerial` 沿用 `IsValidSerial` 校验。
- **自愈与容错**：启动时若 `RunAtStartup` 为 true，会重新登记一次 Run 项，顺带修好 exe 换路径或 Run 项被清理的情况。目录不可写、文件读不了时退回内存默认值并由托盘提示一次，不阻断启动。
- **保留在注册表的两样东西**：`HKCU\...\Run\AdbDeviceVitals` 是 Windows 的启动登记（`--startup` 靠命令行参数判断，不读注册表）；旧键里的 `MigratedTo` 是迁移状态。两者都不是用户配置。
- **不动的地方**：CSV 日志与 `tether.log` 仍在 `%LOCALAPPDATA%\AdbDeviceVitals\logs`。CI 的 zip 里本来就只有 exe、README、LICENSE，配置文件由程序首次运行生成；迁移到框架依赖单文件 exe 后仍然只发布一个 exe，自更新只替换它、配置天然保留。唯一新增的是目标机器要有 **Microsoft Windows Desktop Runtime 10**，这个由安装说明承担，不进 zip。

## 实现说明：USB 网络共享掉线自动恢复

设置项 `AutoRecoverUsbTethering`，默认关闭，保存在 `settings.json`。判定逻辑放在 `Services/UsbTetherWatchdog.cs`，是纯状态机：不碰 ADB、不读系统时间，时间由调用方传入，便于在 `ParserTests` 里推时钟验证。

- **数据来源**：复用 `DeviceMonitor` 每 2.5 秒一轮的 `DeviceSnapshot.UsbTetheringActive`（`dumpsys tethering` 每 12 秒真正读一次，命令失败时沿用上一轮的值，不会把「读不到」当成「掉线」）。不新增定时器，也不额外下发探测命令。
- **状态门槛**：`_wasActive` 记录是否观察到过共享开启，避免程序一启动就把用户本来关着的共享打开；`AutoEnableUsbTethering` 打开时通过 `assumeWasActive` 放宽这个门槛，启动瞬间的掉线也能兜住。
- **三级节流**：`CheckInterval = 20s` 限制判定频率，`ConfirmWindow = 20s` 要求连续读到未开启，`RetryCooldown = 60s` 限制失败重试。切换 USB 功能会让 ADB 重枚举，频繁重试只会让链路更不稳。
- **并发**：`MainWindow` 把 `_usbTetherRunning`（开机自动开启）和 `_usbWatchdogRunning`（守护自身）合并成 busy 传给状态机；恢复任务用独立的 `CancellationTokenSource`，退出时取消。手动 USB 开关移除后，原先的 `_tetherSwitchBusy` 字段一并删除。
- **复用开启链路**：调用 `UsbTetheringService.SetEnabledAsync(true, ...)`，它内部先 probe，返回 `AlreadyActive` 时不会重复下发 `setFunctions`；`ConfirmAsync` 仍按命令下发时的序列号确认设备重新上线，多设备场景不会算到旁边的手机上。
- **手动意图**：`UsbTetherWatchdog` 的 `NoteManualOff` / `NoteManualOn` 与 `_manualOff` 仍保留在状态机里（`ParserTests` 覆盖），但主窗口已无手动开关，运行时不再产生 `NoteManualOff`；设置页把守护从关改成开时仍调 `NoteManualOn` 重置状态。托盘提示：开始尝试与恢复成功各一次，失败只在第一次弹气泡；手机侧共享状态不占主界面，放在「网速」卡片 ⓘ 打开的网络详情弹窗里。
- **不碰热点链路**：守护结果不走 `StartPcHotspotIfPending`，自动开热点仍然只在开机链路里触发一次。

## 实现说明：短信通知同步

需求口径：**应用打开之后开始监听，打开之前的短信不管**；界面上要有近期短信列表。不要求实时推送。

- **方案选择**：ADB 增量轮询 `content://sms/inbox`，不装手机 App、不 Root、不加依赖。对比过 `dumpsys notification --noredact`（通知被划掉就漏、会顺带读到其它 App 的正文、格式随 ROM 变）和手机端 `SMS_RECEIVED` 广播（要第二个工程、国产 ROM 保活成本高），都不如直接读短信库可靠。
- **实测口径**（验证机型 M2102K1AC / Android 14 / MIUI V816）：`cmd appops get com.android.shell READ_SMS` 默认 allow；`--projection` 用冒号分隔，`--sort '_id DESC'`、`--where 'date>N'` 均生效，**`--limit` 不支持**（报 Unsupported argument）；空结果输出 `No result found.`；`adb shell date +%s` 可作时间基线。Windows 侧把 where 用单引号包住，`>` 不会被当成重定向（用 C# `AdbClient.RunShellAsync` 原样跑过）。
- **基线而不是 max id**：用户明确不看历史，用手机时钟做基线最干净，启动时一次 `date +%s` 就够，不必为了拿最大 `_id` 去翻近万行收件箱。每轮查 `date > 基线`，游标推进到「本轮最大 date − 2 秒」，靠 `_id` 集合去重吸收重叠窗口；游标只前进不后退。
- **解析**：`body` 放在 `--projection` 最后，按 `Row: <序号>` 分段，段内除首行外都并回正文（实测 15 条记录占 28 个物理行，确有正文换行）；`IndexOf("body=")` 之后整段算正文，只有前面的 `_id/address/date` 按逗号切。没有 `_id` 的行直接丢，避免反复弹同一条通知。`Parsing/SmsRowParser.cs` 是纯函数，测试里用合成数据覆盖逗号、等号、换行、权限错误和空结果。
- **节流与并发**：挂在 `MainWindow` 每 2.5 秒的采集上，`SmsInboxService` 内部节流到 10 秒并用 `_running` 挡并发；调用处不 await，避免一条 content query 拖慢整轮状态刷新。设备序列号变化时重建基线并清空列表，不把两台手机的短信混在一起。多设备沿用 `TargetDeviceSerial` 的仲裁结果。
- **存储与隐私**：`SmsMessage` 只存在 `_messages` 列表（上限 100 条）和 `_seen` 去重集合里，重启即清空。不进 `DeviceSnapshot`，不写 CSV / `tether.log`，不上传。主窗口预览行与托盘/Toast 提醒都不带正文，`SmsWindow` 默认也不显示正文；「复制正文 / 复制验证码」会进剪贴板，Toast 会进通知中心历史，README 已写明。
- **开关语义**：`SmsSyncEnabled` **默认关闭**（旧配置文件缺该字段也按关闭处理），关闭时连基线都不建立；从关改成开时 `ResetBaseline()` 重建，不补报关闭期间的短信，但已收到的列表保留。
- **正文按需展开**：`SmsWindow` 的 `_showBody` 默认 false，窗口一关就复位，不写进配置。列表内容列用打码占位符，详情框只给发件人和时间；点「显示正文」才把预览列、详情框和「复制正文」放开。含验证码的消息在隐藏状态下只标 `[含验证码]`，不显示码值。状态文字长度会变，每次改状态都要 `PositionStatus()` 重新靠右，否则会跑出窗口（渲染探针抓到过）。
- **验证码**：`Parsing/SmsCodeExtractor.cs` 纯函数，先找「验证码 / code / OTP」等关键词后 4–8 位数字，再看全文是否恰好只有一个独立 4–6 位数字块；余额、订单、日期类关键词直接排除。`SmsWindow` 的「复制验证码」与主窗口托盘菜单「复制最新验证码」只把码写进剪贴板，不需要展开正文，也不在提醒文案里带码值。
- **发件人过滤**：`SmsSenderFilter` 字段（逗号、分号、竖线、空格分隔）经 `Parsing/SmsSenderFilter.cs` 的 `ShouldNotify` 只决定**要不要弹提醒**，不影响采集与列表内容，留空表示全部提醒。过滤纯函数有单测覆盖。
- **Windows 通知**：早期 `Services/WindowsToastService.cs` 反射调用 WinRT `ToastNotificationManager` / `ToastNotification` / `XmlDocument`，运行时对象是 `__ComObject`，`Show` 要从 `CreateToastNotifier` 声明的返回类型上找（与热点服务同一个坑）。**迁移后改为 CsWinRT 强类型**：`ToastNotificationManager.CreateToastNotifier(AppUserModelId)` + `ToastNotification(XmlDocument)`；`App.OnStartup` 在建窗口前用 `SetCurrentProcessExplicitAppUserModelID` 设置 AUMID。不做点击激活（需要 COM 激活器与快捷方式），点击请用托盘菜单。任何一步失败就置 `_unavailable` 并永久回退托盘气泡，避免每条短信都抛异常；`SmsToastEnabled` 可在设置里关掉。本机探针实测 `CanTry=True`、`TryShow=True`。
- **失败处理**：`IsPermissionDenied` 单独识别 `Permission Denial` / `READ_SMS` / `SecurityException`，给中文排障提示并在托盘提醒一次；命令失败、超时、手机时钟读不到都走同一条错误通道，不会静默变成「没有新短信」。成功后清除错误标记，下次失败还能再提示。
- **验证**：`ParserTests` 有解析与配置断言，主窗口、设置页、短信窗口都有渲染截图；另用只读探针在真机上跑过「建立基线 → 增量读 15 条 → 下一轮去重 0 条 → 开关关闭」全链路，探针不输出任何短信正文。

## 实现说明：WPF / .NET 10 全量迁移

原项目是 WinForms + .NET Framework 4.6，用系统自带的 C# 编译器编成零依赖单 exe。这套约束是为了"拷一个 exe 就能跑"，代价是 WinRT 全靠反射、界面只能手绘。在确认「这个工具基本就我自己使用、硬约束可以去掉」之后，整体迁到 WPF + .NET 10，界面按 Windows 11「设置」重做。

架构变化：

| 层 | 迁移前 | 迁移后 |
|---|---|---|
| 工程 | old-style csproj，显式 `<Compile Include>` | SDK-style `net10.0-windows10.0.19041.0`，`UseWPF` + `UseWindowsForms` |
| 入口 | `Program.Main`（WinForms） | `App.xaml` / `App.xaml.cs`，`ShutdownMode=OnExplicitShutdown` |
| 窗口 | `MainForm` / `SettingsForm` / `SmsForm` | `MainWindow` / `SettingsWindow` / `SmsWindow`（XAML + code-behind） |
| 视觉 | 三套互不一致的自绘配色 | WPF-UI 4.3.0：`FluentWindow` + Mica、`TitleBar`、`Card`、`ToggleSwitch`、浅色 `ThemesDictionary` |
| 图表 | WinForms `Control` + GDI+ | `Controls/HistoryChart.cs`：WPF `FrameworkElement` + `DrawingContext`，采样上限与双轴算法不变 |
| WinRT | 反射 `NetworkOperatorTetheringManager` / Toast | CsWinRT 投影强类型 API（见上文两节） |
| 托盘 | WinForms `NotifyIcon` | 仍是 WinForms `NotifyIcon`（WPF-UI 没有托盘控件） |
| 网络 | `WebRequest` / `ServicePointManager` | `UpdateChecker` 改用 `HttpClient`；`Process.Start(new ProcessStartInfo(url) { UseShellExecute = true })` |

业务逻辑（`DeviceMonitor`、`AdbClient`、`DeviceSelection`、`UsbTetherWatchdog`、`SmsInboxService`、`SettingsFile`、`AppSettings`、各解析器）一行没改行为，只是换了承载它的窗口。迁移前先存了本地基线提交 `157d563`，再用两个独立探针分别验证 Windows SDK 投影和 WPF-UI 控件 API，避免在主工程里盲改。

构建与发布：

- `build.ps1` 改为 `dotnet publish -p:PublishSingleFile=true -p:SelfContained=false`。产物仍是一个 exe（约 32 MB，WPF-UI 等托管程序集都打进 bundle），但**目标机器必须装 Microsoft Windows Desktop Runtime 10**；`EnableCompressionInSingleFile=true` 在这个发布模式下会报 `NETSDK1176`，不能用。
- 发布包 / 自更新链路不需要改：zip 里还是 exe + README + LICENSE，`UpdateChecker.ExtractPackage` 只提这三个文件并替换当前 exe，配置在用户目录、不受影响。实测 exe 32,433,808 字节、Deflate 压缩后 zip 约 9 MB，远低于更新器的 30 MB 上限。
- `release.yml` 增加 `actions/setup-dotnet@v4`（`dotnet-version: 10.0.x`），Release notes 写明运行时要求。
- `test.ps1` 现在跑两段：SDK-style 逻辑测试工程（`ParserTests.dll`）和渲染测试工程（`RenderSmokeTest.dll`），输出 6 张图：`wpf-main.png`、`wpf-main-hover.png`、`wpf-main-alt.png`、`wpf-network-details.png`、`wpf-settings.png`、`wpf-sms.png`。

踩过的坑：

- 系统 PATH 上的 `dotnet.exe` 可能只有 host 没有 SDK；脚本优先探测 `%USERPROFILE%\.dotnet\dotnet.exe --list-sdks`。
- PowerShell 5.1 会把无 BOM 的中文脚本按 ANSI 解析，中文注释会导致语法错乱；`build.ps1` / `test.ps1` 的注释保持纯 ASCII。用反引号给 `-p:...` 续行会被解释成命令，改成参数数组 `& $dotnet @publishArgs`。
- `RenderTargetBitmap` 只渲染 WPF 可视树，拿不到 DWM 画的 Mica 背景，截图会变黑 / 变白；渲染测试改为真实 `Application.Run()` 消息循环 + Win32 `GetWindowRect` + `Graphics.CopyFromScreen`。窗口一关 `Application` 会自动 shutdown，所以设成 `OnExplicitShutdown` 并在 `Startup` 里一次性渲染三个窗口。
- **锁屏时 `CopyFromScreen` 只能抓到桌面壁纸**（`LogonUI.exe` 在跑），截图看着像"程序没渲染"。`test.ps1` 检测该进程后自动设 `ADV_RENDER_OFFSCREEN=1`，`RenderSmokeTest.Save` 走 `RenderTargetBitmap` 分支并临时把窗口背景设成白色，产出 960×780 / 880×640 / 800×540 的布局图；Mica 效果要解锁后再跑一次才会出现在截图里。
- `Start-Process -Wait` 在同时存在 `HTTP_PROXY` 和 `http_proxy` 的环境里报「已添加项」；渲染测试改成 `OutputType=Exe` 后用 `dotnet RenderSmokeTest.dll` 同步跑。
- WPF-UI v4 的 `IsBackButtonVisible` 是 `NavigationViewBackButtonVisible` 枚举（`Collapsed` / `Visible` / `Auto`），写 `False` 会抛 `XamlParseException`。
- **设置页侧栏最终没有用 `NavigationView`**：它自带一块内容区，塞进 216px 窄列时菜单文字会被裁成「ADB」「短信·」；试过 `IsPaneOpen` / `OpenPaneLength` / `PaneDisplayMode` 都无法让菜单完整显示，改成自绘的 `RadioButton` 导航栏（白色选中块 + 蓝色指示条），五项文字全部可见。
- 主窗口压缩间距后，「电脑热点」「近期短信」两行都能进首屏；`HistoryChart` 把绘图区顶部从 22 下移到 32，让图例单独占一行，轴最大值不会被叠在「温度 / 信号」上。
- 后续按用户要求**移除了两处冗余说明**：标题下的「通过本机 ADB 读取，每 2.5 秒刷新」和底部「更新于 … / USB 网络共享已…」状态行。前者是静态说明、后者与「网络共享」卡片及开关重复。对应清理 `UpdatedText` / `TetherStatusText` 和 `ShowTetherStatus` 的全部调用；采集异常详情改挂在顶部设备状态的 ToolTip，USB 共享的失败/结果本来就走托盘气泡 `Notify`，切换任务的异常也补了一条气泡，避免删掉状态行后错误静默。

- **首行卡片空白排查（当前状态）**：用户红框指出第一张卡片标题上方一大片空白。逐像素量得三卡标题 y 不齐（211 / 205 / 199），卡片白底高 219px 而内容只有约 100px。三个叠加原因：① WPF-UI `ui:Card` 主题样式**自带 Padding**（上下共约 48px），与 StackPanel `Margin="10"` 叠成双重内边距；② Card 的 `VerticalContentAlignment` 不是 Top，内容被垂直居中，内容越少的卡片标题越低；③ 第一卡隐藏的 `NetworkInfoButton`（20×20，`Visibility=Hidden` 仍占位）在标题 Grid 右列把整行撑高。修法：三卡显式 `Padding="0"` + `HorizontalContentAlignment="Stretch" VerticalContentAlignment="Top"`；第一卡 Content 改成 `Grid`，ⓘ 用 `HorizontalAlignment=Right VerticalAlignment=Top Margin="0,10,10,0"` 叠加定位，不参与 StackPanel 布局（hover 事件与渲染测试断言不变）。结果：卡片白底高 219→171px，三卡标题 y=172/173/175（≤3px 字形差），顶部空白消失，外框仍等大。
